# دليل اختبارات أمان قاعدة البيانات

## الهدف

التحقق قبل التطبيق البعيد من أن RLS والمنح ودوال السيرفر تمنع الطالب/المدرّس من تجاوز صلاحيات المالك.

## الملفات

| الملف | الدور |
|---|---|
| `supabase/tests/security_suite.sql` | السيناريوهات الأمنية |
| `scripts/run-security-tests.mjs` | مشغّل محلي آمن |
| `npm run test:security` | اختصار التشغيل |

## متطلبات البيئة

- قاعدة **LOCAL/disposable** من نوع Supabase فقط
- أدوار: `anon`, `authenticated`, `service_role`
- جدول `auth.users`
- تطبيق كل ملفات `supabase/migrations` أولاً
- `psql` متاح للمشغّل
- اتصال المالك/`postgres` يمكنه `SET ROLE`

## ماذا يختبر الـ suite فعليًا

1. **تبديل دور PostgreSQL الحقيقي** عبر `set_config('role', …)` (مكافئ آمن لـ `SET ROLE` داخل الدوال لأن `SET ROLE` يُلغى عند خروج الدالة)، مع التحقق من `current_user` ورفض أدوار `BYPASSRLS`.
2. كتالوج `lessons_catalog` كـ **anon حقيقي**: درس منشور فقط، بلا `video_asset_id`.
3. الطالب لا يغيّر الدور/`phone_verified_at`، ولا يكتب enrollments/assignments، ولا يعدل الدفع، ولا يوافق/ينشر.
4. المدرّس يعدّل فقط الكورس المعيّن، ولا يوافق دفعًا ولا ينشر ولا يعيّن نفسه.
5. المالك يوافق على الدفع، ينشر، ويعيّن المدرّسين.
6. Idempotency للموافقة + تجديد بعد التعليق مع بقاء تسجيل نشط واحد.
7. انتهاء الصلاحية يمنع الوصول للدرس.
8. ضبط GUC من العميل لا يمنح كتابة enrollments تحت دور `authenticated`.

## سيناريوهات التزامن (غير مغطاة داخل نفس الجلسة)

الاختبارات الحالية تعمل داخل **معاملة/جلسة واحدة**. لذلك لا تثبت وحدها سباقات متزامنة.

| السيناريو | لماذا يحتاج جلسات منفصلة | طريقة مقترحة لاحقًا |
|---|---|---|
| موافقتان متزامنتان على نفس `payment_request` | `FOR UPDATE` يظهر أثره بين جلسات مختلفة | جلستان `psql` أو `pgbench` |
| إنشاء طلبَي `pending` متزامنين لنفس الطالب/المنتج | فهرس فريد جزئي يحتاج تعارض حقيقي | جلستان متوازيتان |
| تجديد وتعليق متزامنان لنفس التسجيل | ترتيب الأقفال بين عمليات مختلفة | جلستان + ترتيب متعاكس |

وثّق نتيجة تلك الاختبارات قبل الإنتاج.

## التشغيل

```bash
# بعد supabase start / db reset محليًا
npm run test:security

# أو يدويًا
psql "$LOCAL_SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/security_suite.sql
```

النجاح الحقيقي يتطلب ظهور:

```text
SECURITY_SUITE_PASSED
RESULT=ok
```

## إن تعذّر التشغيل

إذا لم يتوفر Docker أو `psql` أو قاعدة محلية، النتيجة المتوقعة:

```text
RESULT=skipped
```

وفي هذه الحالة **لا يُعتبر الاختبار ناجحًا** وتبقى البنود أعلاه غير مثبتة تشغيليًا.
