# المرحلة 04 — مصادقة رقم الهاتف + كلمة المرور (بدون OTP في الواجهة)

## تجربة المستخدم المستهدفة

### تسجيل الدخول `/login`
1. رقم محمول مصري
2. كلمة المرور
3. دخول مباشر إلى اللوحة المناسبة بعد نجاح الجلسة

### التسجيل `/register`
1. الاسم الكامل
2. رقم محمول مصري
3. كلمة المرور + تأكيدها
4. **لا توجد شاشة OTP** في المسار الطبيعي

### صفحات أخرى
| المسار | الحالة |
|---|---|
| `/verify-phone` | **متقاعدة** من المسار الأساسي؛ تعيد التوجيه إن وُجدت جلسة، وإلا توضّح الاعتزال |
| `/forgot-password` | تشرح بصراحة أن استعادة SMS غير مفعّلة؛ المسار المدعوم = مساعدة المالك بعد التحقق من الهوية |
| `/reset-password` | تعمل فقط مع جلسة مصادقة صالحة (ليست عبر OTP ذاتي) |
| `/auth/setup-required` · `/auth/inactive` | فشل مغلق كما هو |
| `/student` · `/teacher` · `/admin` | حراس خادم من `profiles` دون تغيير |

## ما يدعمه Supabase وما لا ندّعيه

### مدعوم نظريًا (Phone + password)
- Supabase Auth يدعم `signUp({ phone, password })` و`signInWithPassword({ phone, password })`.
- كلمات المرور تُدار داخل Auth (GoTrue) — **لا** نخزّن كلمات مرور في جداول مخصّصة ولا ننفّذ hashing يدويًا ولا نختلق جلسات.

### شرط حرج للتسجيل بدون SMS
- إذا بقيت **Phone confirmations** مفعّلة، قد يُنشأ المستخدم **بدون جلسة** ويُتوقَّع إرسال OTP.
- المنصة **لا تتجاوز** ذلك صامتًا ولا توجّه لشاشة OTP في المسار الأساسي.
- بدلًا من ذلك: بوابة جاهزية `NEXT_PUBLIC_AUTH_PHONE_CONFIRMATIONS_DISABLED` + رسالة `needs_configuration` إن لم تُرجع `signUp` جلسة.

### غير مدعوم / مرفوض عمدًا
| السلوك | القرار |
|---|---|
| OTP SMS في التسجيل/الدخول | خارج تجربة المنصة الحالية |
| اختراع بريد وهمي لتجاوز الهاتف | مرفوض |
| جدول كلمات مرور مخصّص / hashing يدوي | مرفوض |
| تعليم الرقم `verified` تلقائيًا بدون تحقق | مرفوض |
| اعتبار إدخال الرقم إثبات ملكية | مرفوض — الرقم معرّف هوية فقط بدون إثبات حيازة |
| endpoint عام لتزويد أدمن/مدرّس أو كلمة مرور مشتركة | مرفوض |
| استعادة ذاتية عبر SMS | غير مفعّلة؛ نوثّق المساعدة اليدوية من المالك |

### بديل آمن إن تعذّر تعطيل التأكيدات
- تزويد حسابات الطلاب من المالك عبر أدوات الخدمة (`service_role` خارج المتصفح) مع عملية تحقق هوية مناسبة.
- أو الإبقاء على التسجيل العام مغلقًا خلف بوابات الجاهزية حتى يتوفر مسار مدعوم صراحةً.

## متغيرات البيئة (بوابات تفشل مغلقًا)

راجع `.env.example`:

| المتغير | المعنى |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | اتصال العميل العام |
| `NEXT_PUBLIC_AUTH_PHONE_PASSWORD_READY` | تم التحقق يدويًا أن Phone identity + password جاهزان |
| `NEXT_PUBLIC_AUTH_PHONE_CONFIRMATIONS_DISABLED` | تم تعطيل تأكيدات الهاتف في Auth عمدًا |
| `NEXT_PUBLIC_DB_SCHEMA_READY` | هجرات `profiles`/RLS مطبّقة ومؤكّدة |

- توافق خلفي: `NEXT_PUBLIC_AUTH_PHONE_PROVIDER_READY` ما زال يُقبل كاسم قديم لبوابة الهاتف.
- **لا** تضع `service_role` في `NEXT_PUBLIC_*` أو المتصفح.
- استعادة كلمة المرور الذاتية عبر SMS **ليست** بوابة جاهزية قابلة للتفعيل في هذه المرحلة (`canSelfServePasswordRecovery = false` دائمًا في الكود).

## حدود ملكية الهاتف

- تطبيع E.164 للمصري في `src/lib/auth/phone.ts`.
- uniqueness على مستوى القاعدة مخطّط في الهجرات المحلية — يُفعَّل فقط بعد تطبيقها عن بُعد بموافقة.
- إدخال الرقم أثناء التسجيل/الدخول **لا** يثبت أن الطالب يملك الشريحة.
- الصلاحيات تُقرأ من `profiles.role` / `is_active` على الخادم فقط — وليس من «حيازة الهاتف».

## استعادة كلمة المرور (صادق)

1. لا وعد بإرسال SMS.
2. `/forgot-password` يعرض تعليمات موحّدة دون كشف وجود الحساب.
3. المسار المدعوم حاليًا: تواصل مع إدارة المنصة → تحقق هوية → إعادة تعيين عبر أدوات المالك الآمنة.
4. `/reset-password` لمن لديه جلسة صالحة فقط (مثل بعد تدخل إداري)، وليس نتيجة OTP عام.

## منع الإساءة (متطلبات + ما هو منفّذ محليًا)

| الطبقة | الحالة |
|---|---|
| حد معدّل بدائي داخل العملية (`src/lib/auth/rate-limit.ts`) | منفّذ للتطوير؛ ليس كافيًا للإنتاج الموزّع |
| حدود Supabase Auth / Dashboard | مطلوبة عند التفعيل |
| CAPTCHA / WAF / حد موزّع (Redis/Upstash) | مطلوبة قبل الإنتاج |
| عدم كشف وجود الحساب في الاستعادة/التسجيل المكرّر | منفّذ في الرسائل |
| تزويد `super_admin` / `teacher` | من المالك فقط عبر workflows الهجرات — ليس من الواجهة العامة |

## ملفات أساسية

- `src/lib/auth/readiness.ts` — بوابات جاهزية
- `src/lib/auth/actions.ts` — دخول/تسجيل/استعادة/تحديث كلمة المرور بدون OTP
- `src/lib/auth/rate-limit.ts` — حد محاولات بدائي
- `src/lib/auth/guards.ts` / `profile.ts` — حراس الأدوار كما هي
- `src/components/auth/*` — نماذج عربية RTL بلون بنفسجي داكن

## الاعتماد على الهجرات

- التسجيل الكامل وحراسة الأدوار يعتمدان على `profiles` وtrigger الطالب.
- بدون `NEXT_PUBLIC_DB_SCHEMA_READY`: الحراس يفشلون مغلقًا → `/auth/setup-required`.
- الهجرات ما زالت **محلية فقط** — لم تُطبَّق عن بُعد في هذه المرحلة.

## ما يعمل الآن مقابل ما هو معطّل

| العنصر | الحالة |
|---|---|
| واجهات `/login` و`/register` بدون OTP | جاهزة |
| تطبيع الهاتف المصري | جاهز |
| حراس الأدوار من الخادم | جاهزة (تفشل مغلقًا بدون schema) |
| تسجيل/دخول فعلي عبر Auth | معطّل حتى بوابات الجاهزية = true وإعداد المشروع |
| مسار OTP في الواجهة | متقاعد |
| استعادة SMS ذاتية | معطّلة عمدًا |
| تطبيق الهجرات عن بُعد / النشر | لم يُنفَّذ |
| المرحلة 06 | لم تبدأ |

## اختبار آمن لاحقًا (بعد موافقة)

1. مشروع disposable فقط.
2. فعّل Phone provider؛ عطّل Phone confirmations إن رغبت بالمسار بدون OTP.
3. طبّق الهجرات على ذلك المشروع فقط.
4. اضبط بوابات `.env.local` بعد التحقق اليدوي.
5. سجّل طالبًا → يجب جلسة مباشرة؛ إن لم توجد جلسة توقف ولا تتجاوز.
6. اختبر رفض طالب لـ `/admin` و`/teacher`.
7. لا تستخدم `service_role` في المتصفح.

## ملاحظة أمان

لا يُدعى اكتمال المصادقة من طرف إلى طرف لأن إعداد Auth وهجرات القاعدة لم يُؤكَّدا تشغيليًا بعد. البوابات تفشل مغلقًا عن قصد.
