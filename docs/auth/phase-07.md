## مسار الدخول المقصود (هاتف مصري + كلمة مرور بدون OTP)

الكود الحالي يدعم:

1. `/login` → `signInWithPassword({ phone, password })` بعد تطبيع E.164 (`+20…`)
2. `/register` → `signUp({ phone, password })` للطالب فقط، بدون شاشة OTP
3. إن لم تُرجع `signUp` جلسة → رسالة إعداد صريحة (`needs_configuration`) دون تجاوز

### إعدادات Auth المطلوبة في لوحة Supabase (يدوي)

لا يمكن الجزم آليًا من CLI بحالة مزوّد الهاتف في هذه البيئة. يجب التحقق يدويًا:

1. **Authentication → Providers → Phone**: مفعّل كمعرّف هوية.
2. **Confirm phone / Phone confirmations**: **معطّل** إذا رغبت بجلسة مباشرة بدون SMS.
3. عدم الاعتماد على OTP كمسار دخول أساسي للمنصة.
4. ضبط حدود المعدّل وCAPTCHA قبل فتح التسجيل العام.

بعد التحقق اليدوي فقط يمكن ضبط:

- `NEXT_PUBLIC_DB_SCHEMA_READY=true` (الهجرات مؤكدة)
- `NEXT_PUBLIC_AUTH_PHONE_PASSWORD_READY=true`
- `NEXT_PUBLIC_AUTH_PHONE_CONFIRMATIONS_DISABLED=true` (بعد تعطيل التأكيدات فعلًا)

**لا تُفعَّل هذه الأعلام في هذه الخطوة.**

## مخاطر ملكية الهاتف غير المُثبَتة

عند تعطيل تأكيد SMS:

- إدخال الرقم **لا يثبت** حيازة الشريحة.
- أرقام المحمول قد تُعاد تدويرها؛ من يحصل على الرقم لاحقًا قد يحاول استعادة/إنشاء تعارض.
- المهاجم قد يسجّل أرقامًا لا يملكها ويحجز حسابات أو يُربك الطلاب.

### حماية مقترحة

| الطبقة | الإجراء |
|---|---|
| استعادة كلمة المرور | مساعدة المالك بعد تحقق هوية خارج القناة العامة (الوضع الحالي في `/forgot-password`) — بدون وعد SMS |
| حد المعدّل | موجود بدائيًا في التطبيق؛ للإنتاج: حدود Auth + CAPTCHA + حد موزّع |
| MFA للمالك | مستحسن بشدة لحساب `super_admin` حتى مع هاتف+كلمة مرور |
| عدم تعليم `phone_verified_at` تلقائيًا | محفوظ في المخطط؛ لا يُعلَّم بدون تحقق حقيقي |
| تزويد المالك | خارج التسجيل العام عبر `service_role` فقط |

## قيود الأدوار في الكود والقاعدة

- `handle_new_user` يفرض دائمًا `role = student` ويتجاهل أي دور من metadata.
- التسجيل العام لا يمرّر `role` أصلًا.
- `admin_set_user_role` **يرفض** ترقية إلى `super_admin`.
- `provision_super_admin`:
  - يتطلب JWT `service_role` فقط
  - مرفوض عن `anon` / `authenticated`
  - يمنع مالكًا ثانيًا عبر فهرس جزئي + فحص صريح
- واجهات المدرّس/المالك محمية بحراس خادم من `profiles`

## عملية التزويد لمرة واحدة (مُجهَّزة — غير منفَّذة)

السكربت المحلي: `scripts/provision-owner.mjs`

1. يتحقق أن لا يوجد `super_admin`.
2. يطلب رقمًا مصريًا + موافقة صريحة + مفتاح `service_role` من بيئة الجهاز فقط.
3. ينشئ مستخدم Auth بالهاتف وكلمة مرور عبر Admin API (خادمي).
4. يستدعي `provision_super_admin(user_id, full_name, phone)`.
5. يطبع نجاحًا بدون كشف كلمة المرور أو المفتاح أو المعرّفات الحساسة بالكامل.

**الوضع الافتراضي: جافٍ (`--dry-run`). التنفيذ الفعلي يتطلب موافقتك الصريحة ورقم الهاتف.**

## الخطوة التالية التي تحتاج موافقة

1. تزوّد برقم الهاتف المصري للمالك (E.164 أو صيغة محلية تُطبَّع).
2. تؤكد إعداد Auth (Phone مفعّل + Confirm phone حسب القرار).
3. تضع `SUPABASE_SERVICE_ROLE_KEY` محليًا في بيئة الطرفية فقط (ليس في Git / ليس `NEXT_PUBLIC_*`).
4. توافق صراحةً على تشغيل التزويد لمرة واحدة.
